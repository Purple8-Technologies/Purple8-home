01 · The Problem

Research toolchains were not built
for relational data at scale.

Every quantitative research project reaches the same wall: data that is inherently relational — households within districts, sensors within networks, papers within citation graphs — squeezed into flat tables that discard the structure that makes the analysis meaningful.

Where standard tools fail
  • R / Stata / SPSS load entire datasets into RAM — 5M+ row surveys exhaust 64 GB workstations
  • Spatial packages (spdep, GeoPandas) require manual contiguity matrix assembly — O(n²) memory for large grids
  • No native graph traversal: multi-hop household-to-district-to-state relationships require repeated joins
  • Reproducibility via script files — no immutable audit trail of which transformation ran on which version of which data
  • Collaboration requires shared file systems or copying datasets — version drift inevitable
The fragmentation cost
6+tools for one analysis pipeline (R, PostGIS, Neo4j, Elasticsearch, Zotero, Stata)
Daysto assemble spatial weights matrix for a national-level DHS survey
0graph databases that run air-gapped on a research workstation without a DBA
The reproducibility gap

R Markdown and Quarto documents record code, not data state. If an upstream CSV changes, no audit trail identifies when the change happened, who ingested it, or which downstream results are now stale.

04 · Spatial Analysis

Moran's I and LISA
as first-class graph operations.

Purple8 stores the spatial weights matrix as graph edges — the same structure used for every other graph operation. Moran's I runs directly over that adjacency, with no intermediate matrix assembly step and no R session required.

What ships out of the box
  • Global Moran's I — analytical moments (Cliff & Ord 1981): E[I], Var[I], z-score, two-tailed p-value
  • 999-permutation pseudo p-value — recommended when the variable is non-normal; configurable 0–9 999
  • Row-standardised W — comparable across different graph densities by default; binary W available
  • LISA (local_morans_i) — per-node Iᵢ with conditional permutation test; HH / LL / HL / LH / NS classification
  • cluster_summary() — count of each cluster type across the study area at a chosen alpha
# Single call — no spdep, no shapefile, no CRS
result = morans_i(engine._storage, "District",
  value_property="u5_stunting_pct",
  weight_edge_type="BORDERS",
  permutations=999)
# → I=0.62, z=4.8, p=0.001 → "Positive spatial autocorrelation"

07 · Reproducibility

Every transformation, every query,
stored as an immutable graph edge.

The audit trail is not a log file — it is part of the graph itself. Every `INGEST_FROM`, `DERIVED_FROM`, and `QUERIED_AT` edge is written before the mutation completes (WAL-first) and cannot be deleted or overwritten.

What gets recorded automatically
  • Which source file each node was derived from, with SHA-256 hash
  • Timestamp of every ingestion event (UTC, nanosecond precision)
  • Which API key / user triggered each operation (JWT or API key identity)
  • Which algorithm version produced which result set
  • When a dataset was replaced — prior version remains queryable
For journal submission and replication

Replication package in one command

Export the full audit subgraph for any result set: every input dataset, every transformation parameter, every intermediate node — all with timestamps and data hashes. Attach to supplementary materials. Reviewers can verify the chain of custody without re-running the analysis.

Multi-round survey compatibility

NFHS-3, NFHS-4, NFHS-5 can coexist in the same graph as separate subgraphs, each version-tagged. Cross-round comparisons run as graph queries — no manual reconciliation of variable naming changes.

Why the memory model matters for research

Most survey databases (PostgreSQL with PostGIS, Neo4j) project memory usage by multiplying per-record size by N. BrickCoreStorage does not work this way.

The Cortex storage engine seals and evicts completed batches — pages are returned to the OS after each batch. Peak RSS oscillates in a fixed envelope determined by available RAM, not corpus size.

Consequence: a research group's shared 32 GB workstation handles NFHS-5 (636 000 households), all 640 districts as spatial nodes, and the full citation corpus in the same process — simultaneously.

636 000 households, 640 districts, one graph.

Large-scale demographic health surveys collect data that is inherently hierarchical and spatial — households nested in PSUs, PSUs in districts, districts in states — but almost all analysis treats it as flat. Purple8 makes the structure native.

What becomes possible
  • Moran's I over district-level stunting rates — identify spatial clusters without assembling a contiguity matrix in R first
  • LISA: which specific districts are HH (hot spots) vs HL (outliers) at p < 0.05
  • Graph traversal: which districts border high-burden districts, and what is their own burden? (one 2-hop query)
  • Shortest path: from any enumeration block to nearest ICDS centre — service coverage gap map in seconds
  • Cross-round: NFHS-4 vs NFHS-5 as parallel subgraphs — delta query without manual variable reconciliation

10 · Use Case — Sensor Network Research

Industrial IoT and environmental
monitoring: graph-native from the sensor up.

Sensor networks are graphs. Each node is a physical device; edges are communication links, spatial adjacency, or shared infrastructure. Purple8 ingests telemetry streams, maintains the network topology, and runs spatial and network analysis over it — without a separate time-series database.

What becomes native
  • Spatial autocorrelation of readings — does particulate matter cluster spatially? Moran's I over sensor-node properties answers in one call
  • Fault propagation tracing — betweenness centrality identifies which sensor nodes are structural bottlenecks in the communication graph
  • Community detection — Louvain clustering groups sensors by communication pattern, revealing implicit network zones
  • Bridge detection — find_bridges() identifies single points of failure before they cause network partition
  • Anomaly context — when a sensor fires an alert, graph traversal retrieves all adjacent sensors and their readings in one hop
Example: air quality monitoring grid
# Does PM2.5 cluster spatially across the grid?
result = morans_i(engine._storage,
  node_label="Sensor",
  value_property="pm25_24h_avg",
  weight_edge_type="SPATIAL_ADJACENT",
  permutations=999)

# Find the network's critical sensors
bc = betweenness_centrality(engine._storage, top_k=10)
EDAμS compatibility

Sensor metadata, calibration records, and maintenance logs ingested via DocIntel alongside telemetry streams. Calibration drift modelled as a time-varying edge property. The graph is the digital twin.
